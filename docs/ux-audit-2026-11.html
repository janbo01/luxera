Luxera UX Audit

Every customer-facing route in luxera/ was checked at phone width (375px) and desktop width (1440px), together with the header, mobile menu, bottom nav, search overlay, cart drawer and login modal. Each page was compared against its source code. Most of the store works well. The problems that cost money sit in checkout and on the contact page. The polish work is mostly about making pages consistent with each other.

Update · 13 November 2026

Status: fixed in code

Every finding below has been worked through in the storefront, the order and store services, and the admin panel. Nothing is committed or deployed yet. The two database migrations still need to run on production.

Found while fixing, now fixed too: the order service never charged shipping, so the amount sent to the payment gateway left out the 120k–280k shipping shown at checkout. Snapp Box showed a made-up "was ۳۲۰٬۰۰۰" price. The address form said "verified with Irancell" for any 10-digit number. Phone fields dropped Persian digits. The product breadcrumb linked to /category/<uuid>, which is not a route. And a CSP gap blocked the script that hands server-rendered page data to the client, so pages re-fetched data they already had.

Corrections to this audit: the signed-out account page was not blank; it has a guest view, which the login modal covered on arrival (the modal no longer opens by itself). Each product card exposes only one add-to-cart button to screen readers, because the two are split by media query. The gift finder already had shareable result links.

Priority order

Fix these first

These five issues either lose orders or break a promise to the customer. The first three are a few hours of work each.

  1. Gift wrapping is shown and charged in the summary but never reaches the order

    The shipping step offers بسته‌بندیِ هدیه for 15,000 toman with "a handwritten card", and the order summary adds it to the total. handlePay never sends it, so the backend prices the order without it and nobody packing the parcel knows a gift was wanted. There is also no field for the card message.

    views/CheckoutPage.tsx:234 · components/checkout/ShippingStep.tsx:216 · components/checkout/OrderSummary.tsx:158

  2. The contact form shows "sent" but sends nothing

    handleSubmit waits 900 ms and then shows the success state. Every message typed into it is lost, and the customer believes the team will reply within 24 hours.

    views/static/ContactPage.tsx:58

  3. Guests complete all three checkout steps, then fail at Pay

    Nothing asks a signed-out visitor to log in. They fill the address, choose shipping and press Pay. createAddress then returns a 401, and the client shows the raw error text with no login prompt. Ask for the phone number and OTP first, inside checkout, and keep the form state through it.

    views/CheckoutPage.tsx:212 · api/client.ts:47

  4. Delivery promises disagree across six places

    A Tehran customer is told 4–6 hours, 24 hours and "one-day" depending on the page, and the methods named on the shipping page are not the ones checkout offers. The full comparison is in the table under Site-wide patterns.

    data/shipping.ts is the right single source

  5. "Fine Jewelry" under the logo contradicts what the store sells

    The header and login modal say Fine Jewelry. Every description says جواهرات فانتزی (fashion jewelry). Iranian shoppers are wary of gold claims, so the tagline undercuts the honest positioning that the About page argues for. It also renders at 9px.

    components/layout/Header.tsx:304 · components/account/LoginModal.tsx:115
Consistency

Site-wide patterns

Most of the "make it cleaner and more organized" work comes from here. Each pattern repeats across many pages, so fixing it once in a shared component tidies the whole store. None of these depend on the active theme, and all of them use the existing --lx-* tokens.

Four different page-header styles

Medium
  • A boxed card (PageIntro) on Collections, a collection, and Blog. It fills about 40% of the first phone screen.
  • An English uppercase kicker on About, Contact, FAQ, Shipping, Privacy and Terms.
  • An italic English kicker on Checkout.
  • A Persian kicker with a rule on Wishlist and Gift. Breadcrumbs appear on some of these pages and not others.

Do: one PageHeader with a breadcrumb, an H1, an optional one-line intro and an optional meta line (count, date), all unboxed. Use it on every non-home page.

English decorative labels in a Persian store

Medium
  • About, Contact, FAQ, Shipping & returns, Privacy, Terms, Checkout
  • Customer reviews, What our clients say, The Story, Thank you, Gift Wrapping, Fine Jewelry

Do: drop them, or write them in Persian. Keep Latin only for the "Luxera" wordmark.

Four type families

Medium
  • Morabba for headings, Yekan Bakh for body text
  • Cormorant Garamond italic, used 24 times
  • JetBrains Mono, used 74 times (counters, labels, prices)

Do: use Morabba and Yekan Bakh only, with tabular Persian digits for prices and counters. This is the biggest single change for a calmer, more modern feel, and it removes two font downloads.

Too much fixed chrome at the bottom of phone screens

Medium
  • On a category page, the Filter/Sort bar sits on top of the bottom nav. That is about 120px of fixed UI on an 812px screen.
  • The add-to-cart toast lands on top of the Filter/Sort bar.

Do: hide the bottom nav while a listing's tool bar or the product page's buy bar is showing, or merge them into one bar. Anchor toasts above whatever bar is visible.

Three product-card variants

Low
  • ProductCard on listings, search and carousels
  • A separate card on the Wishlist page with a different image ratio, price layout and button

Do: make Wishlist render ProductCard with a "saved price" slot.

Small type and mixed digit systems

Low
  • 9px "FINE JEWELRY", and 11px text in six places
  • Phone placeholders use Latin digits (912 345 6789) while the rest of the page uses Persian digits
  • Price-chip filters are 36px tall, and a few links are under 44px

Do: set 12px as the minimum size, use Persian digits everywhere the shopper reads, and make tap targets at least 44px.

Two H1s and duplicated structured data

Low
  • Home, category and product pages each have an sr-only SEO H1 as well as the visible H1
  • The home page JSON-LD is declared in both index.astro and HomePage.tsx, with different descriptions and phone fields

Do: keep one H1 (the visible one, carrying the SEO wording) and one JSON-LD block, rendered on the server.

Brainstorm

Feature ideas

These ideas fit how Luxera actually works: about 100 products, mostly one or two units each, admin-chosen themes, OTP accounts, loyalty points and an AI blog. They avoid scarcity badges and colour pickers, which the current cart cannot support.

Quick wins days

Phone-first checkout

ConversionFrontend

Make the first checkout step a phone number and OTP, then pre-fill name and phone. This fixes the guest failure at Pay and shortens the form.

Points you'll earn

LoyaltyFrontend

Show "earns N points" on the product page and in the cart, using loyalty_earn_percent from settings. The program exists, but shoppers only see it at checkout.

Smarter empty search

DiscoveryFrontend

Popular searches, category chips and Persian character normalisation in the overlay.

Help deep links

SupportFrontend

Give every FAQ answer an anchor, and point the footer, product tabs and contact page at the exact answer.

Medium projects 1–2 weeks

Real gifting

GiftingOrder service

Gift wrap and card message saved on the order, "ship to someone else", and a packing slip without prices. Luxera already sells mostly gifts.

Needs order fields and an admin view

Weekly drops

RetentionStore + SMS

Group new pieces into dated drops, with a "notify me about the next drop" sign-up by SMS or a Bale/Telegram channel. One-of-a-kind stock becomes a reason to come back.

Sold, see similar

SEODiscovery

Keep sold product pages live with a clear "sold" state and a similar-items rail, instead of a dead end or a 404. They keep their search ranking.

Guest order tracking

SupportOrder service

Look up an order by order number and phone, with a status timeline and the Tipax or Post tracking code. This cuts "where is my order" messages.

Wishlist alerts

RetentionSMS

An SMS when a saved piece drops in price, using the savedPrice the wishlist already stores.

Contact inbox in admin

SupportStore service

Store contact messages, list them in admin with a status, and reply over SMS or WhatsApp.

Bigger bets a month or more

Colour variants end to end

CatalogueCart + orders

Carry color_id through the cart, checkout and orders, then add swatches to cards. Today a colour chosen on the product page is lost, which is why customers type colours into order notes.

Backend first: cart lines and order items

Photo reviews after delivery

TrustProduct + SMS

Send an SMS a few days after delivery with a one-tap review link. Reviews with customer photos are the strongest proof for fashion jewelry.

Pay in instalments

ConversionPayments

Offer a buy-now-pay-later option from an Iranian provider at checkout, for baskets above a threshold.

Needs a provider contract

Installable app (PWA)

RetentionFrontend

Add to home screen, an offline shell, and web push for drops and order updates. It pairs well with the bottom nav, which already feels like an app.

Method

How this was checked

The production API was unreachable, so the store was built as a production bundle and served against a read-only fixture API with placeholder products, categories, collections, posts and banners. Placeholder images and stock states are not reported as findings.

Each route was rendered at 375×812 and 1440×900 and checked for overflow, tap-target size, text under 12px, missing labels and heading structure. The automated contrast scan was too noisy on sections using content-visibility to be trusted, so no contrast findings are listed. The theme engine already guarantees 4.5:1.

Not exercised live: signed-in account panes, the payment redirect and the order-success return. Those findings come from reading the code. All visual recommendations use the existing theme tokens, so they hold for every theme the admin can choose.
